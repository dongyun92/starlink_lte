## 1. 시스템 개요

### 1.1 목적 및 역할

비행 통신 품질 데이터 수집 시스템은 무인 항공기(드론) 운용 중 발생하는 통신 품질 데이터를 수집·저장·병합하여 후속 분석에 제공하는 플랫폼이다.

본 시스템은 다음의 핵심 목표를 수행한다:

- **다중 소스 통합**: 이기종 데이터 소스(위성 통신, 지상 셀룰러, 비행 컨트롤러)에서 발생하는 데이터를 단일 타임라인으로 통합한다.
- **세션 기반 관리**: 개별 비행 임무를 독립적인 세션(UUID)으로 격리하여 데이터 혼용을 방지한다.
- **비동기 처리**: 파일 업로드와 분석 파이프라인을 분리하여 대용량 파일(최대 500MB)을 처리할 수 있는 비블로킹 아키텍처를 제공한다.
- **품질 보증**: 센티넬 값 필터링, 타임스탬프 검증, 결측값 보간 등을 통해 분석 전 데이터 품질을 보장한다.

### 1.2 데이터 소스 구성

수집 대상은 총 3가지 데이터 소스로 구성된다:

| 소스 | 장비 | 포맷 | 샘플링 주기 |
|------|------|------|-----------|
| Starlink 위성 단말 | SpaceX Starlink Dish | CSV | 1초 (1 Hz) |
| LTE 모뎀 | 4G LTE 모뎀 (예: NetGear, Quectel) | CSV | 1초 미만 (sub-second) |
| 비행 컨트롤러 | Pixhawk (PX4 펌웨어) | ULG (binary) | GPS: ~5 Hz, Attitude: ~100 Hz |

> **비행 로그(ULG)는 필수** 입력이며, LTE 및 Starlink 데이터는 선택적으로 업로드할 수 있다. 비행 로그가 없는 경우 업로드는 거부된다.

## 2. 데이터 소스별 수집 항목

### 2.1 Starlink 위성 데이터

Starlink 단말에서 수집되는 데이터는 SpaceX gRPC API 또는 전용 데이터 수집기(collector)를 통해 CSV 형식으로 저장된다. 파일당 수집 주기는 1초 간격이다.

#### 수집 필드 목록

| 필드명 | 단위 | 설명 |
|--------|------|------|
| `timestamp` | UTC datetime | 데이터 수집 시각 (ISO 8601 형식) |
| `downlink_throughput_bps` | bps (bits per second) | 위성→단말 실시간 다운링크 전송량 |
| `uplink_throughput_bps` | bps (bits per second) | 단말→위성 실시간 업링크 전송량 |
| `latency` | ms (milliseconds) | 위성 왕복 지연시간 (RTT, Round-Trip Time) |
| `pop_ping_latency_ms` | ms | PoP(Point of Presence) 핑 지연시간 |
| `ping_drop_rate` | 0.0 ~ 1.0 | 핑 손실률 (0: 손실 없음, 1: 100% 손실) |
| `snr` | dB (decibel) | 신호대잡음비 (Signal-to-Noise Ratio). 높을수록 양호 |
| `obstruction_percentage` | % (0 ~ 100) | 장애물에 의한 하늘 차폐율 |
| `is_roaming` | boolean (0/1) | 로밍 상태 여부 |
| `uptime` | seconds | 현재 연결 세션의 유지 시간 |

#### 데이터 품질 기준

- **SNR 정상 범위**: 0 ~ 15 dB (15 dB 이상은 excellent, 0 dB 미만은 연결 불가)
- **latency 정상 범위**: 20 ~ 600 ms (위성 특성상 최소 20 ms)
- **센티넬 값**: `-999`는 센서 오류를 의미하며, 파이프라인에서 `NaN`으로 자동 변환됨
- **pop_ping_latency_ms**: `-1` 값은 측정 실패를 의미하며 자동 필터링됨

#### 파생 컬럼 (분석 시 자동 생성)

| 파생 컬럼명 | 원본 컬럼 | 변환 |
|-------------|----------|------|
| `starlink_download` | `downlink_throughput_bps` | bps → Mbps (÷ 1,000,000) |
| `starlink_upload` | `uplink_throughput_bps` | bps → Mbps (÷ 1,000,000) |
| `starlink_latency` | `pop_ping_latency_ms` 또는 `ping_latency_ms` | 컬럼명 정규화 |
| `starlink_available` | `starlink_latency` | latency ≠ NaN이면 True |

### 2.2 LTE 모뎀 데이터

LTE 모뎀에서 수집되는 데이터는 AT 커맨드 또는 전용 수집 소프트웨어를 통해 CSV 형식으로 저장된다. 수집 주기는 1초 미만(sub-second)이다.

#### 수집 필드 목록

| 필드명 | 단위 | 설명 |
|--------|------|------|
| `timestamp` | UTC datetime | 데이터 수집 시각 |
| `rsrp` | dBm | Reference Signal Received Power. 기지국으로부터 수신되는 참조 신호 전력. 범위: -140 ~ -44 dBm |
| `rssi` | dBm | Received Signal Strength Indicator. 전체 수신 신호 강도. 범위: -120 ~ -25 dBm |
| `sinr` | dB | Signal to Interference+Noise Ratio. 신호 대 간섭+잡음 비율. 범위: -20 ~ +30 dB |
| `rsrq` | dB | Reference Signal Received Quality. 참조 신호 수신 품질. 범위: -20 ~ -3 dB |
| `network_band` | integer | LTE 밴드 번호 (예: 1, 3, 5, 7, 8, 28 등) |
| `pcid` | integer | Physical Cell ID. 물리 셀 식별자 (0 ~ 503) |
| `earfcn` | integer | E-UTRA Absolute Radio Frequency Channel Number. 주파수 채널 번호 |
| `enodeb_id` | integer | 기지국(eNodeB) 식별자 |
| `cell_id` | integer | 셀 식별자 |
| `rx_bytes` | bytes | 수신 누적 바이트 수 |
| `tx_bytes` | bytes | 송신 누적 바이트 수 |
| `dl_bandwidth` | MHz | 다운링크 채널 대역폭 (1.4, 3, 5, 10, 15, 20 MHz) |
| `ul_bandwidth` | MHz | 업링크 채널 대역폭 |
| `connection_state` | string | 연결 상태 (예: `LTE_CONNECTED`, `DISCONNECTED`, `SEARCHING`) |

#### 신호 품질 기준 (3GPP 표준)

| 지표 | 우수 | 양호 | 보통 | 불량 |
|------|------|------|------|------|
| RSRP | > -80 dBm | -80 ~ -90 dBm | -90 ~ -100 dBm | < -100 dBm |
| SINR | > 20 dB | 13 ~ 20 dB | 0 ~ 13 dB | < 0 dB |
| RSSI | > -65 dBm | -65 ~ -75 dBm | -75 ~ -85 dBm | < -85 dBm |
| RSRQ | > -10 dB | -10 ~ -15 dBm | -15 ~ -20 dB | < -20 dB |

#### 센티넬 값 처리

- `rsrp`, `rssi`, `rsrq`, `sinr` 필드에서 `-999` 값은 센서 오류를 의미하며 자동으로 `NaN` 처리됨
- `lte_available` 파생 컬럼: `rssi` ≠ NaN이면 True로 설정됨

### 2.3 비행 로그 데이터 (ULG)

PX4 펌웨어가 탑재된 Pixhawk 비행 컨트롤러는 비행 중 모든 센서 데이터를 ULG (uLog) 바이너리 포맷으로 SD 카드에 기록한다.

#### ULG 포맷 개요

- **파일 확장자**: `.ulg`
- **구조**: 바이너리 스트림으로, 메시지 타입(message type)별 데이터셋이 포함됨
- **타임스탬프**: 부팅 이후 경과 시간(microseconds), 절대 UTC 시간으로 변환 필요
- **파싱 도구**: `pyulog` 라이브러리 (`ULog` 클래스)

#### 추출 데이터셋

시스템은 ULG 파일에서 다음 두 개의 데이터셋을 우선적으로 추출한다:

**① vehicle_gps_position** (주 GPS 데이터)

| 필드명 | 단위 | 설명 |
|--------|------|------|
| `timestamp` | microseconds | 부팅 이후 경과 시간 |
| `time_utc_usec` | microseconds (UTC epoch) | UTC 절대 시각 (가용 시 최우선 사용) |
| `latitude_deg` 또는 `lat` | degrees | WGS84 위도 |
| `longitude_deg` 또는 `lon` | degrees | WGS84 경도 |
| `altitude_msl_m` 또는 `alt` | meters | 평균 해수면 기준 고도 (MSL) |
| `cog_rad` | radians | Course Over Ground (대지 방향각), 0~2π |

> **Fallback**: `vehicle_gps_position`이 없을 경우 `vehicle_global_position` 데이터셋을 사용한다.

**② vehicle_attitude** (자세 데이터)

| 필드명 | 단위 | 설명 |
|--------|------|------|
| `timestamp` | microseconds | 자세 데이터 수집 시각 |
| `q[0]` | 무차원 | 쿼터니언 스칼라 성분 (w) |
| `q[1]` | 무차원 | 쿼터니언 벡터 성분 (x) |
| `q[2]` | 무차원 | 쿼터니언 벡터 성분 (y) |
| `q[3]` | 무차원 | 쿼터니언 벡터 성분 (z) |

#### 쿼터니언 → 오일러 각도 변환

자세 데이터는 쿼터니언으로 저장되며, 분석 편의를 위해 다음 수식으로 오일러 각도(degrees)로 변환한다:

```
# Quaternion: (q0, q1, q2, q3) = (w, x, y, z)

Roll  (X축 회전) = arctan2(2*(q0*q1 + q2*q3), 1 - 2*(q1² + q2²))
Pitch (Y축 회전) = arcsin(2*(q0*q2 - q3*q1))
Yaw   (Z축 회전) = arctan2(2*(q0*q3 + q1*q2), 1 - 2*(q2² + q3²))
```

변환 결과는 degrees 단위로 GPS 데이터에 병합된다. GPS 타임스탬프와 attitude 타임스탬프 간 최대 허용 오차는 **100ms**이며, 이를 초과하는 경우 해당 포인트의 자세 값은 `NaN`으로 처리된다.

#### GPS 헤딩(Heading) 계산

`cog_rad` 필드(Course Over Ground)를 대지 방향각(heading)으로 변환한다:

```
heading_deg = degrees(cog_rad) % 360   # 0 ~ 360도 범위로 정규화
```

#### ULG 타임스탬프 절대 시각 변환 전략

ULG 내부 타임스탬프는 부팅 이후 경과 시간(μs)이므로 절대 UTC 시각으로 변환해야 한다. 다음 3가지 방법이 우선순위 순으로 적용된다:

| 우선순위 | 방법 | 조건 |
|---------|------|------|
| 1순위 | `time_utc_usec` 필드 직접 사용 | GPS 데이터셋 내 유효한 UTC 타임스탬프 존재 시 |
| 2순위 | CSV 데이터의 시작 시간을 기준점으로 사용 | LTE 또는 Starlink CSV의 `timestamp` 최솟값 활용 |
| 3순위 | 파일명에서 시각 추출 | 파일명 패턴 `YYYYMMDD_HHMM` 파싱 후 KST→UTC 변환 (UTC = KST - 9h) |
| 4순위 (최후) | 상대 시간 그대로 사용 | 위 방법이 모두 실패한 경우 (정확도 저하 경고 발생) |

## 3. 데이터 업로드 파이프라인

### 3.1 Flask 웹 서버

- **서버 포트**: 5002
- **최대 업로드 크기**: 500 MB (`MAX_CONTENT_LENGTH`)
- **허용 파일 형식**: `.ulg`, `.csv`
- **CORS 설정**: 활성화 (프론트엔드 분리 구성 지원)

### 3.2 업로드 엔드포인트

```
POST /api/upload
Content-Type: multipart/form-data
```

**요청 파라미터**

| 파라미터 | 타입 | 필수 여부 | 설명 |
|---------|------|---------|------|
| `flight_log` | file (`.ulg`) | **필수** | PX4 비행 로그 파일 (복수 파일 가능) |
| `lte_data` | file (`.csv`) | 선택 | LTE 모뎀 데이터 파일 (복수 파일 가능) |
| `starlink_data` | file (`.csv`) | 선택 | Starlink 단말 데이터 파일 (복수 파일 가능) |
| `metadata` | JSON string | 선택 | 세션 메타데이터 (`name`, `date`, `location` 등) |

**응답 (HTTP 201)**

```json
{
    "session_id": "a3b4c5d6-...",
    "status": "uploaded",
    "created_at": "2026-02-26T10:30:00",
    "message": "파일 업로드가 완료되었습니다. 분석이 백그라운드에서 진행 중입니다."
}
```

### 3.3 세션 기반 관리 구조

파일이 업로드되면 UUID v4 기반의 세션 ID가 할당되며, 해당 ID로 격리된 디렉토리가 생성된다:

```
analysis/uploads/
└── {session_id}/                      ← UUID v4 (예: a3b4c5d6-7e8f-...)
    ├── flight_logs/
    │   ├── flight_20260212_1030.ulg
    │   └── flight_20260212_1045.ulg   ← 복수 ULG 파일 지원
    ├── lte_data/
    │   ├── lte_session1.csv
    │   └── lte_session2.csv           ← 복수 LTE CSV 파일 지원
    └── starlink_data/
        └── starlink_session1.csv      ← 복수 Starlink CSV 파일 지원
```

### 3.4 세션 상태 전이

세션은 SQLite 데이터베이스(`sessions.db`)에서 다음 상태를 순차적으로 거친다:

```
pending → uploaded → processing → completed
                              └──→ failed
```

| 상태 | 진행률 | 설명 |
|------|--------|------|
| `pending` | 0% | 세션 생성 직후 초기 상태 |
| `uploaded` | 5% | 파일 저장 완료, 분석 대기 중 |
| `processing` | 10 ~ 99% | 분석 파이프라인 실행 중 |
| `completed` | 100% | 분석 성공적으로 완료 |
| `failed` | 가변 | 분석 중 오류 발생 |

### 3.5 재분석 엔드포인트

실패한 세션에 대해 재분석을 요청할 수 있다:

```
POST /api/retry/{session_id}
```

분석이 진행 중인 세션(`processing` 상태)은 재분석이 거부된다.

## 4. 데이터 병합 프로세스

### 4.1 개요

세 가지 데이터 소스를 단일 타임라인으로 통합하기 위해 타임스탬프 기반 비동기 병합(`merge_asof`)을 사용한다. 분석 파이프라인의 Step 1에서 수행된다.

### 4.2 ULG → CSV 변환

```python
from pyulog import ULog
ulog = ULog(str(ulg_path))

# vehicle_gps_position 데이터셋 추출
gps_dataset = next(d for d in ulog.data_list if d.name == 'vehicle_gps_position')
```

ULG 파일은 `pyulog` 라이브러리로 파싱하여 GPS 및 attitude 데이터를 pandas DataFrame으로 변환한다.

### 4.3 다중 파일 통합

복수의 ULG, LTE CSV, Starlink CSV 파일은 각각 `pd.concat()`으로 수직 결합된 후 병합 대상이 된다. 각 비행 로그 파일에는 고유한 `flight_id`(0, 1, 2, ...)와 `flight_name`(파일명)이 부여된다.

### 4.4 3-way 비동기 병합

GPS 데이터를 기준(left)으로 하여 Starlink, LTE 데이터를 순차적으로 `merge_asof`로 병합한다:

```
GPS Data (기준) ──┐
                  ├→ merge_asof ─→ [GPS + Starlink] ──┐
Starlink Data ───┘  (tolerance: 2s)                   ├→ merge_asof ─→ merged_data.csv
                                                        │  (tolerance: 2s)
LTE Data ──────────────────────────────────────────────┘
```

**병합 파라미터**

| 파라미터 | 값 | 설명 |
|---------|---|------|
| `on` | `timestamp` | 기준 컬럼 |
| `direction` | `nearest` | 가장 가까운 타임스탬프 매칭 |
| `tolerance` | `pd.Timedelta('2s')` | 최대 허용 시간 오차 ±2초 |

> GPS 데이터가 없는 경우, Starlink와 LTE를 `merge` (outer join)로 결합하는 fallback 로직이 적용된다.

### 4.5 컬럼 네임스페이스 분리

병합 시 컬럼명 충돌을 방지하기 위해 소스별 접두사(prefix)를 적용한다:

| 소스 | 원본 컬럼명 예시 | 병합 후 컬럼명 |
|------|---------------|--------------|
| LTE | `rsrp` | `lte_rsrp` |
| LTE | `rssi` | `lte_rssi` |
| LTE | `sinr` | `lte_sinr` |
| Starlink | `snr` | `starlink_snr` |
| Starlink | `downlink_throughput_bps` | `starlink_downlink_throughput_bps` |
| GPS (ULG) | `latitude` | `latitude` (접두사 없음, 기준 데이터) |

### 4.6 데이터 정제 처리

병합 완료 후 다음 처리가 순차적으로 수행된다:

1. **센티넬 값 필터링**: `-999`, `-1` 등 오류 값을 `NaN`으로 변환
2. **결측값 보간**: GPS 좌표(`latitude`, `longitude`, `altitude`)에 선형 보간(`interpolate(method='linear')`) 적용
3. **파생 변수 생성**:
   - `distance_moved`: 연속 GPS 포인트 간 Haversine 거리 (meters)
   - `speed_mps`: 이동 속도 (m/s)
   - `distance_from_origin`: 출발점으로부터의 누적 거리 (meters)
   - `flight_time_elapsed`: 비행 경과 시간 (seconds)
4. **중복 컬럼 제거**: `df.loc[:, ~df.columns.duplicated()]`

### 4.7 출력 파일

병합 완료된 최종 데이터는 다음 경로에 저장된다:

```
analysis/results/{session_id}/merged_data.csv
```

이 파일이 이후 모든 분석(Step 2 ~ Step 6)의 입력 데이터로 사용된다.

### 6.3 SQLite 데이터베이스 스키마

**sessions 테이블**

```sql
CREATE TABLE sessions (
    id            TEXT PRIMARY KEY,          -- UUID v4
    name          TEXT NOT NULL,             -- 세션 이름
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status        TEXT NOT NULL DEFAULT 'pending',  -- 상태
    progress      INTEGER DEFAULT 0,         -- 진행률 (0-100)
    current_step  TEXT,                      -- 현재 단계 설명
    metadata      TEXT,                      -- JSON 문자열
    file_paths    TEXT                       -- JSON 문자열 (파일 경로 목록)
);
```

**analysis_results 테이블**

```sql
CREATE TABLE analysis_results (
    session_id        TEXT PRIMARY KEY,
    correlation_matrix TEXT,    -- JSON: 상관관계 행렬
    key_findings      TEXT,     -- JSON: 주요 발견 사항
    statistics        TEXT,     -- JSON: 통계 요약
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**charts 테이블**

```sql
CREATE TABLE charts (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT NOT NULL,
    chart_name  TEXT NOT NULL,
    file_path   TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

## 7. 오류 처리 및 데이터 품질 보증

### 7.1 파일 유효성 검증

업로드 시 다음 검증이 수행된다:

1. **필수 파일 확인**: 비행 로그(`.ulg`) 파일이 없으면 HTTP 400 반환
2. **확장자 검증**: 허용 확장자(`.ulg`, `.csv`) 이외의 파일은 거부
3. **파일명 보안**: `werkzeug.utils.secure_filename()`으로 경로 탐색 공격 방지
4. **빈 파일 스킵**: 0 rows인 CSV 파일은 로드 단계에서 자동 스킵 (경고 로그 출력)

### 7.2 타임스탬프 일관성 검사

병합 완료 후 각 소스의 시간 범위를 비교하여 불일치 경고를 생성한다:

- 비행 로그, LTE, Starlink 데이터 간 시간 범위 겹침 여부 확인
- 시간 불일치 발견 시 세션 메타데이터(`analysis_results['time_warnings']`)에 경고 기록

### 7.3 분석 실패 복구

- 백그라운드 분석 스레드에서 예외 발생 시 세션 상태가 `failed`로 전환됨
- `POST /api/retry/{session_id}` 엔드포인트를 통해 재분석 가능
- `processing` 상태의 세션은 재분석 요청이 거부됨 (동시 실행 방지)
